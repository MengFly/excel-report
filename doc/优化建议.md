## 一、框架现状

基于 POI + SpEL 的 Excel 报表生成框架，核心设计：

- **模板驱动**：XML 模板 → ContainerTreeNode 树 → ParserFactory 按标签分发 → Container 组件树
- **三段式渲染**：onMeasure（测量）→ onLayout（定位）→ export（写单元格）
- **样式系统**：StyleKey 反射映射到 POI setter，StyleChain 用栈实现层级继承，ReportContext 内做 CellStyle/Font 池化
- **数据注入**：SpEL 表达式 ${...}，DataContext extends HashMap，支持 for/if 流程控制

整体架构清晰、分层合理。问题主要集中在易用性细节、渲染性能热点、以及若干扩展性硬编码上。

## 二、易用性

### 1. ~~TemplateManager 单例非线程安全，且模板每次重新解析~~ ✅ 已解决
`template/TemplateManager.java:16-22` 双重检查缺失单例，并发下可能创建多个实例。
`getTemplate(id)` 每次调用都重新读流 + DOM 解析，`include` 标签还会级联触发。
**原建议**：单例改为 static final 或 holder 模式；对解析结果做缓存。

**实现**：
- 单例改为 `private static final TemplateManager instance = new TemplateManager()`，由 JVM 类初始化保证唯一性与可见性（原描述"双重检查缺失"不准确，静态初始化本就是线程安全的）；
- 新增 `Map<String, ReportTemplate> templateCache = new ConcurrentHashMap<>()`，`getTemplate` 改为 `computeIfAbsent`：同 id 只解析一次，不同 id 可并发解析；
- `templateFactory` 加 `volatile`（字段可变，需可见性保证）；
- 新增 `clearCache()` / `clearCache(String id)`，供模板热更新场景强制失效。

**后续**：缓存后 `ReportTemplate` 对象被长期复用，原先担心的共享可变状态是 `templateManager` 字段（原 H1）——
该字段与 `render(TemplateManager, DataContext)` 已随 `696704d` 一并删除（见第六节），
当前模板对象在 render 期只读（`ContainerTreeNode` 的 `parent` / `element` / `syleMap` 构造后不再写，`Container` 每次 render 新建）。
⚠️ 同模板多线程 render 尚无压测验证，结论仅基于静态代码。

### 3. ~~表达式缓存是实例级、无上限控制~~ ✅ 已解决
`ExpressionHelper.java:20` 的 LRUCache<>(256) 每个实例一份，而 DataContext.Builder.build()
默认 new ExpressionHelper()，导致每次 build 都是新缓存，热点表达式反复走 SpEL 解析。
**原建议**：Expression 对象跨实例复用。

**实现**：改为**类内静态共享缓存** `SHARED_EXPRESSION_CACHE`（`LRUCache<>(2048)`），而非单例。
- `ExpressionHelper()` 无参构造使用共享缓存；新增 `protected ExpressionHelper(Cache)` 供子类隔离或测试注入；
- `DataContext` 一行未改（`:13` / `:62` 的 `new ExpressionHelper()` 语义不变，只是底层缓存变为全局共享）；
- 新增 `static clearSharedCache()`，主要用于测试隔离；
- 容量 256 → 2048：原为"每上下文一份"，现为"全应用一份"。

**收益定位（诚实评估，勿高估）**：
单模板**单次**渲染几乎零收益 —— 实例级缓存的作用域是 helper 生命周期，而一次 render 内 helper 是复用的
（`ForExpression.createForEnv` → `createChildContext` 复用父 helper），重复表达式本来已命中。
例：Table 100 行 × 3 列 ≈ 600 次 `doExpression`，但不同字符串仅约 6 个 → 实例缓存已提供 ~99% 命中率。

真实收益只有两类：
| 场景 | 原因 | 量级 |
|---|---|---|
| **`<include>` 位于循环内** | `IncludeParser:33` 每次 include 调用都 `new DataContext()` → 新 helper → **新缓存**，导致每轮迭代重新解析该 include 模板的全部表达式。这是"单模板单次渲染"内的真实重复劳动 | 迭代数 × include 表达式数 × ~10–30 µs |
| **同 JVM 内多次渲染同一模板**（报表服务 / 批量导出 / 插件反复预览） | 每次渲染新建 helper → 缓存重置 | (渲染次数 − 1) × 不同表达式数 × ~10–30 µs |

模板通常含 20–200 个不同表达式 → 单次渲染省 0.2–6 ms。相对大表渲染（数百 ms）占比 <1%，对小报表可能占百分之几十。

**结论**：这不是性能优化，是"消除一处重复劳动"。20 行代码 + 零 API 破坏，做了不亏，但**不应按 P1 排期**。
真正有数量级差异的是三.4（auto 列宽）与三.6（SXSSF）。

**为什么不用单例 `getInstance()`**：插件侧 `PreviewExpressionHelper` 持有 per-render 的 `warnings` 列表（有实例状态），必须 `new` 而非取单例；单例只能覆盖默认路径，插件拿不到共享缓存，优化会完全失效。静态缓存在子类实例上同样生效。

**共享安全性论证**（已核实）：
1. 缓存的是 AST，不含数据 —— `NotExpression`(仅 String) / `StandardExpression`(仅 SpEL Expression，不可变) / `ComposeExpression`(仅 List)，字段全 final，均不引用 `DataContext`；
2. 数据绑定在求值期 —— `StandardExpression.evaluate` 调 `TemplateExpression.getEvaluationContext(dataContext)`（`:19-24`，default 方法）**每次新建** `StandardEvaluationContext`，rootObject 为当次上下文；Spring 的 `Expression` 语义即"解析一次、多 context 多次求值"；
3. 解析结果只依赖字符串 —— `parser` 为 static `SpelExpressionParser`，无按模板/上下文的配置差异；
4. 插件降级逻辑不串味 —— `PreviewExpressionHelper` 的"取不到值降级为原文"写在 `doExpression`（**求值期**）override 里，包在 `super.doExpression` 外层，与解析期缓存无关。

**线程安全**（hutool 5.8.18，已用 javap 反编译核实）：
- `LRUCache extends ReentrantCache`；`ReentrantCache.get(K,boolean)` 用 `ReentrantLock` 全锁；
- `AbstractCache.get(K,boolean,Func0)` 用 `keyLockMap.computeIfAbsent` 做**按 key 加锁**的回填，不同表达式可并发解析；
- ⚠️ 早期 hutool 版本的 `LRUCache` 直接继承 `AbstractCache`、无 `ReentrantLock`，**非线程安全**；若降级 hutool 需自行加锁；
- `LRUCache<>(capacity)` 的 timeout 为 0（永不过期），仅受容量约束。

**行为变更**：`onCreateExpression` 钩子（`:33`）在缓存未命中时回调，共享后**只对"首次解析该表达式"的实例触发一次**。当前框架与插件均未 override，无影响；已在 javadoc 中注明"不得用于挂载实例级状态"。

**唯一遗留（非跨模板问题）**：`ExpressionHelper:70-72` 把**解析失败**降级为 `NotExpression` 并缓存 —— "解析失败"被固化，改模板不会重新解析（除换字符串或 `clearSharedCache`）。同字符串在任何模板下降级一致，语义确定，不构成跨模板异常。

## 三、性能

### 1. ~~StyleChain.onStyle 每次调用都全量重建 StyleMap（最大热点）~~ ✅ 已解决
`style/StyleChain.java:35-39` 的 curStyle() 遍历整个栈重新合并 HashMap。
onStyle 在每个组件 export 时都会调用一次（Container.java:57）。
**原建议**：用 ArrayDeque + 缓存 currentStyle，push 时增量 merge、pop 时回滚；
或改用不可变层的 CombinedStyleMap，查询时按需查找。

**实现**：已改为单栈 `Deque<StyleMap> mergedStack`，每层保存"该层合并后的完整样式表"。
- push：`mergedStack.push(mergeInto(mergedStack.peek(), style))`，只合并当前层，O(key 数)；
- pop：`while (size > depth) pop()`，直接弹回父层结果，O(1)，零重建；
- 原 `styleChain` 栈退化为纯计数器后已删除（`mergedStack` 长度与其完全同步）；
- `getStyle()` 返回 `mergedStack.peek()`，栈空时返回空 StyleMap。

每次 onStyle 由 O(栈深 × key 数) 降为 O(key 数)。

### 2. ~~ReportContext.applyCellWidthHeight 逐行设置行高~~ ✅ 已解决（结论与原建议相反）

**原描述**：`ReportContext.java`（applyCellWidthHeight）当设置 defaultRowHeight 且存在 autoHeight 行时，
遍历 firstRowNum..lastRowNum 逐行 setHeightInPoints，大表下是 O(rows) 额外开销。
**原建议**：只记录需要设置的行区间，或与写入过程合并。

**❌ 原建议错误，已实测否决。** 曾尝试把它换成 sheet 级 O(1) 写法：

```java
sheetStyle.getStyle(SheetStyles.defaultRowHeight).ifPresent(sheet::setDefaultRowHeightInPoints);
```

实测（用真实模板 `src/test/resources/IndexSensitivityTemplate.xml` 导出，产出 `example/IndexSensitivityTemplate.xlsx`）：

| 项 | 值 |
|---|---|
| 文件内 `sheetFormatPr` | `<sheetFormatPr defaultRowHeight="24.0" customHeight="true"/>` |
| 行 1~3 | `<row r="1" ht="62.0" customHeight="true">` 等（autoHeight 行） |
| 行 4~33 | `<row r="4">` —— **无 `ht`** |
| POI `XSSFRow#getHeightInPoints()` | 24.0（按 `isSetHt() ? ht : sheet.getDefaultRowHeightInPoints()` 回落） |
| **Excel 实际显示** | **20** |

**⇒ Excel 不按 `sheetFormatPr@defaultRowHeight` 决定"无 ht 行"的高度**（至少对 POI 写的 `customHeight="true"` 这种形式），
而是按字体自行推算。因此**行高必须逐行写 `ht`**，sheet 级 API 单独使用无效。

**⇒ 由此暴露一个既有 bug（与本次改动无关）**：原代码的循环被 `if (!autoHeightRow.isEmpty())` 包着，
当模板中**没有任何 cell `<height>` 样式**时循环不执行，一行 `ht` 都不写 →
**`<defaultRowHeight>` 完全失效**。例如 `src/test/resources/LargeExportTemplate.xml`
只设了 `<defaultRowHeight>18</defaultRowHeight>` 且无 cell height → Excel 打开实际不是 18。

**实现**：**去掉外层 `!autoHeightRow.isEmpty()` 判断**，让"逐行补 ht"始终执行（autoHeight 行仍跳过）：

```java
// Excel 不认 sheet 级 sheetFormatPr@defaultRowHeight（无 ht 的行会按字体自行推算），
// 因此除已单独设置了高度的行之外，其余行必须逐行写入 ht，否则 sheetStyle 的 defaultRowHeight 不生效。
sheetStyle.getStyle(SheetStyles.defaultRowHeight).ifPresent(height -> {
    for (int i = sheet.getFirstRowNum(); i <= sheet.getLastRowNum(); i++) {
        if (autoHeightRow.containsKey(i)) {
            continue;
        }
        final Row row = sheet.getRow(i);
        if (row != null) {
            row.setHeightInPoints(height);
        }
    }
});
```

**验证**（探针 `Probe4`，模板只设 `<defaultRowHeight>18</defaultRowHeight>`、无任何 cell height）：

```
修复前：<row r="1">          ← 无 ht，Excel 忽略 18
修复后：<row r="1" ht="18.0" customHeight="true"/>
        <row r="2" ht="18.0" customHeight="true"/>
        <row r="3" ht="18.0" customHeight="true"/>
```
`IndexSensitivityTemplate` 场景下数据行也恢复为 `ht="24.0"`，与修复前一致（该模板有 cell height，循环本来就会跑）。

**已知成本**：O(rows) 逐行写入必然发生，且每行会多出 `ht` / `customHeight` 两个属性（约 28 字节/行）。
这是 Excel 正确性的必要成本，不再作为优化目标 —— 原第 1 项"O(rows) 额外开销"的担忧作废。

**诊断材料**：`example/ht-probe/` 下 4 个对照文件（由 `IndexSensitivityTemplate.xlsx` 只改写 `sheet1.xml` 生成），
用于复现 Excel 的取值规则；结论已落地，该目录可随时删除。

| 文件 | `sheetFormatPr` | 行 ht | 现象 |
|---|---|---|---|
| `ht-1-default24-customHeight-true.xlsx` | `24.0` + `customHeight` | 无 | Excel 显示 **20**（≠24，即忽略该属性） |
| `ht-2-default24-no-customHeight.xlsx` | `24.0`，无 `customHeight` | 无 | 对照：验证 `customHeight` 是否元凶 |
| `ht-3-per-row-ht24.xlsx` | `24.0` + `customHeight` | 每行 `ht="24.0"` | Excel 显示 24 ✅ |
| `ht-4-default40-customHeight-true.xlsx` | `40.0` + `customHeight` | 无 | 对照：与 ht-1 现象一致即证明该属性被完全忽略 |

### 3. ~~CellStyle 池化 key 用 StyleMap，getStyleMap 会把缺失 key 塞 null~~ ✅ 已解决（结论修正：无池命中率收益）
`StyleMap.java:28-34` 缺失时放入 null，导致等价样式因 null 占位不同产生不同 key，
池命中率被拉低。
**原建议**：getStyleMap 跳过 null 值，提升池命中率。

**❌ 原假设不成立（已实测否决）。** `getStyleMap` 的**唯一调用点**是 `CellStyles.toFontStyle`
（`CellStyles.java:279`），传入的 key 集合是固定集合 `fontStyleMap.values()`（8 个字体 key）。
既然键集合恒定，写不写 null 占位**不改变任意两个 fontStyle 之间的相等关系**，
⇒ `fontPool`（`ReportContext.java:102`）的命中率前后完全一致。

**实现**：仍按建议改为跳过 null，但收益需重新定位：

```java
public StyleMap getStyleMap(Collection<StyleKey<?>> keys) {
    StyleMap style = new StyleMap();
    for (StyleKey<?> key : keys) {
        final String value = styleMap.get(key.getId());
        if (value != null) {                    // 缺失不写 null 占位
            style.styleMap.put(key.getId(), value);
        }
    }
    return style;
}
```

- **语义修正**：null 值 key 不再算"存在"。取值侧本来就等价 —— `getStyle(key)` 对"缺失"与"值为 null"都返回 `Optional.empty()`（`StyleMap.java:50-55`），而 `createCellStyle` / `createFont` 都是 `containsKey → getStyle → ifPresent`，结果不变；
  ⚠️ 唯一真实差异：直接调 `containsKey` 的地方由 true 变 false（当前仅上述两处，行为等价）。
- **顺带生效**：`ReportContext.getFont` 的 `if (fontStyle.isEmpty()) return null` 由"永不成立"变为"可成立" —— 无任何字体样式的**裸 StyleMap** 不再白造一个 Font 对象。框架路径不受影响（`ExcelReport.java:63` 会把 `CellStyles.DEFAULT_STYLE` 压到样式链底层，字体 key 恒全）。
- **内存**：池 key 由固定 8 项缩小为实有项。

**A/B 实测**（同模板 `IndexSensitivityTemplate.xml` + 同固定数据，旧实现 / 新实现各导出一份）：

| 项 | 结果 |
|---|---|
| zip 条目数 | 均 9 条 |
| `xl/styles.xml` | 归一化后**逐字节相同**（fonts=4 / cellXfs=7 / fills=6 / borders=9） |
| `xl/worksheets/sheet1.xml` | **相同** |
| 唯一差异 | `docProps/core.xml`（仅时间戳） |

**结论**：对渲染结果**零影响**，属"语义 + 内存清理"，**没有性能收益**，**不应按 P1 排期**（20 行内改动、零 API 破坏，顺手做即可）。
真正的命中率瓶颈在 `cellStylePool` 的 key 用的是**原始 merged StyleMap**（`ReportContext.java:36`）：两个组件样式语义等价但 key 集合不同就各建一份 `CellStyle`，要动也是动那里，而非 `getStyleMap`。

### 7. ~~Image 体系与网络图片缺少超时/校验~~ ✅ 已解决（超时部分）
**原问题**：`ReportContext.addPicture`（`ReportContext.java:113-117`）直接 `IoUtil.readBytes`；`UrlImage` 走网络无超时设置。
**建议**：加超时参数与失败降级。

**根因（比原描述严重）**：`UrlImage` 用的是 `ImgUtil.getImage(new URL(url))`，而 hutool 的实现是
`Toolkit.getDefaultToolkit().getImage(url)` —— AWT **异步**加载，导致：
1. 超时**根本设不进去**（`Toolkit` 不接受任何超时参数）；
2. 失败**不抛异常**（错误只进 `ImageObserver`），构造期的 `catch` 形同虚设；
3. 后续 `ImgUtil.toStream` → `toBufferedImage` → `copyImage` 会调 `getWidth(null)` 强制同步等待
   ⇒ 线程**无限期阻塞**在下载上，整个导出卡死。

**实现**（`UrlImage.java`）：改为 `URLConnection` **同步**下载
- `setConnectTimeout` / `setReadTimeout` 显式设置，默认 **5s / 10s**；新增 `UrlImage(url, connectTimeout, readTimeout)` 可覆盖；
  **单参构造保留**（`ImageParser.java:53` 仍在用）⇒ 零 API 破坏；
- HTTP 状态码非 2xx 直接抛 `IOException`，并 `setInstanceFollowRedirects(true)`（图片常经 CDN/短链跳转）；
- `ImageIO.read` 返回 null（不是图片内容）也抛 `IOException`；
- 异常照旧存入 `exception` 字段，`openStream()` 抛出后被 `ImageComponent.onExport` 的 `catch` 接住
  → 单元格降级为错误文本（沿用原有降级路径，未新增机制）；
- 输出仍统一按 JPEG（`ImgUtil.IMAGE_TYPE_JPEG`），**现有导出产物行为不变**。

**实测**（探针 `ProbeUrlImage`，本地 `HttpServer` 模拟三种响应）：

| 场景 | 结果 |
|---|---|
| `/ok` 200 + PNG | 正常，读出 643 字节，`type=jpeg` |
| `/404` | `IOException: Unexpected HTTP status 404 for ...`（旧实现不会报错） |
| `/slow` 连接后不返回任何字节，read=1000ms | 构造耗时 **1007ms** → `SocketTimeoutException: Read timed out` |
| 对照：旧实现 `ImgUtil.getImage` + `toStream` 打同一挂起连接 | **8 秒内未返回（卡死）** ⇒ 证实"无超时可用、只能无限等" |

编译验证：`mvn -o -q -DskipTests compile`（JDK 8）通过。

**未做（如需可另开一项）**：
- **响应体大小上限**：`addPicture` 的 `IoUtil.readBytes` 仍会整图入内存，超大图可 OOM；
- **类型推断**：`imageType` 硬编码 JPEG，PNG 的 alpha 会被丢弃（`StreamImage` 同理），`Image.deduceExcelImageType()` 的 PNG/EMF 分支实际走不到；
- **占位降级**：目前失败是往单元格写错误文本，没有"用占位图代替"的选项。
