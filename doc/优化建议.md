## 二、待办

### P1 · 三.4 auto 列宽计算（真热点）

**现状**：结果累积是增量的（`cellAutoWidth.compute(max)`），**计算不是** —— 每次都调 `SheetUtil.getColumnWidth` 全量重算，
且 `setStyle` 与 `setValue` 各触发一次。成本（1000 行×3 列，Arial 12pt）：

| 合并区数 | 逐 cell 调用 | 按列一次调用 |
|---|---|---|
| 0 | 24.35 µs/cell | 15.05 µs/cell（-38%） |
| 1000 | **541 µs/cell** | 39.86 µs/cell（-93%） |

单次调用固定开销 ≈ 9.3 µs（无合并）；1000 合并区时 ≈ 517 µs/次（**每次都要 `sheet.getMergedRegions()` 复制整个合并区列表**）。
外推 1000 行×10 列全 auto：无合并 487 ms → 150 ms；1000 合并区 10.8 s → 0.4 s。

**⚠️ 正确性前提（否则会改坏结果）**：现状语义是"**只对带 `width=auto` 样式的 cell** 度量再取 max"，
而 POI 的 `getColumnWidth(sheet, col, true, firstRow, lastRow)` 会算区间内**所有** cell。
实测反例：20 行列宽 —— 只算第 0 行 = **2.71**，整列算 = **28.54**（撑大 10 倍）；全行都带 auto 时两者一致。

**已做（方案 1：延迟到终态算一次）** ✅ `f577599`，约 20 行、无 API 变更：

| 文件 | 改动 |
|---|---|
| `ExcelCellSpan` | 新增 `autoSizeCalculated`；`setStyle` 不再计算（只记 `styleMap`）；新增 `calculateAutoSizeIfAbsent()` |
| `ReportContext` | 新增 `cellSpans` 列表并在 `getCellSpan` 登记；`applyCellWidthHeight` **开头**补算未算过的 span |

为什么不能简单删掉 `setStyle` 那次：`SpanComponent` / `ChartComponent` 只 `merge()` 不 `setValue`。
实测 `setStyle` 那次返回 **-1**（cell 空白未 merge，`+4` 后 = 3 的垃圾值），必然被 `setValue` 的终态值覆盖。
**等价性三重验证**：① 真实模板导出改动前后 `sheet1.xml`（含 `<cols>`）**逐字节相同**；
② 只 merge 场景 768 = 768；③ 有值场景 2798 = 2798。收益 **-50%**（48.7 → 24.35 µs/cell）。

**待做**：
- 方案 2 **条件批量**（再降到 ~15 µs/cell）：统计每列"auto cell 数 == 非空 cell 数"才整列一次算，否则退回逐 cell；
- 方案 3 **自实现度量**（收益最大）：POI 的 `getCellWidth` 是 private，想做到"只算 auto cell 的批量"只能自己复制
  `AttributedString`/`TextLayout` + 合并区逻辑，并复用 `FontRenderContext`、自维护合并列表；需与 POI 结果做等价性回归。

### ~~P1 · 四.1 注册表可扩展（SPI）~~ ❌ 已取消（2026-09-29）

**取消理由**：`ParserFactory` 的 13 个 tag（`Text`/`Table`/`Image`/`List`/`HLayout`/`VLayout`/`Link`/`Chart`/`Span`/`include`/`PageRowSplit`/`PageColSplit`/`GridLayout`）
与 XSD `ContainerGroupContainer`（`excel-report-1.0.0.xsd:794-809`）的 `xs:choice` 白名单**逐一对应**；
该 choice **没有 `xs:any`**，`Style`（`:327-583`）也是封闭的 `xs:all`。⇒ 新增 Parser = 新增 XML 标签 = 违反 XSD，
"注册表开放"解决不了 schema 层面的问题。真有自定义需求，只能 fork/扩展 XSD 并同步插件校验（属框架协议变更，不是 SPI 改造）。

### P2 · 二.2 严格模式

只剩 2 处静默 catch 要改（`CellStyles.createStyle`、`BeanUtil`），加开发期抛异常 + `template.validate()` 汇总 issue。
**顺带结论**：框架运行期**完全不校验 XSD**（`src/main` 里没有任何 schema 引用），模板头部的 `xsi:schemaLocation` 只被编辑器/插件用
⇒ 若要"模板校验"，最有价值的做法是按 XSD 校验（能一次抓住所有拼错的标签/属性/key），比逐个 catch 改造收益大。
（原同组的"三.6 SXSSF 流式导出"已取消，见"三、备查"。）

### ~~P2 · 三.6 SXSSF 流式导出~~ ❌ 已取消（2026-09-29）

**取消理由**：框架定位是**复杂报表**（合并区 / 多列布局 / 图表 / 图片 anchor / 精确宽高），
与 SXSSF 的"行序单调 + 行刷盘后可随机访问失效"根本冲突：只换 workbook 无法完成流式，
彻底方案要动 `Container` 的写单元格方式（改走"行模型 / CellSink"中间层），代价与收益不成比例。
**大批量报表请走其他方案**：直接用 POI SXSSF / EasyExcel（FastExcel）/ 流式 CSV，或先落库再导出。
实测依据归档在"三、备查"（仅当以后重新评估时再读）。

### P3 · 四.2 StyleKey 函数式 apply（可选，已缩水）

**实测**：现状 `getMethod + invoke` = 2357 ns/次；函数式 lambda = 1952 ns/次；**只缓存 Method = 1884 ns/次**
⇒ 性能上"缓存 Method"就与全量函数式持平；受样式池化限制，调用次数 = 样式种类数（5–50），总收益 **≤ 0.4 ms**，**性能不是理由**。

**真收益（四.6 取消后只剩这一条）**：方法名/目标类型写错变成**编译期错误**（现在静默失效，只留一行 `log.error`；实测已踩到 `CellStyle` 接口没有 `setReadingOrder`）。
原"② 是四.6 的前置"随四.6 取消而失效 ⇒ 本项降为**可选清理**，不做也不影响任何能力。
另注：仅解耦 apply **不足以**支持 CSV/HTML 输出（`StyleMap→CellStyle`、`ExcelCellSpan` 全链路绑死 POI）。

**路线（前 3 步零 API 破坏）**：新增 `StyleApplier<T>` → `StyleKey` 加 applier 字段、旧构造降级为"反射 applier" →
定义侧加 `cell()/font()/sheet()` 便捷方法（`cell("borderTop", CellStyle::setBorderTop)`）→ （可选、breaking）删 `methodName`/`type`。
分批：`CellStyles` 13 个 cell key → 8 个 font key → `SheetStyles` 26 个 key → `ColorStyleKey` 5+1，共 50 处。
注意 `CellStyle` 接口没有 `setReadingOrder`、`Sheet` 没有 `setDefaultRowHeightInPoints`，lambda 里要强转具体类型。
**对插件零影响**（插件 `StyleKeyInfo.kt` 是自带的 key 名镜像清单，只按 id 匹配，且改造不动 id）。

## 三、已完成项的关键结论（备查）

| 编号 | 结论 |
|---|---|
| 二.1 | 单例 + `ConcurrentHashMap` 缓存；`ReportTemplate` 已无共享可变字段，但**同模板多线程 render 尚无用例验证** |
| 二.3 | 静态共享缓存替代实例缓存。单次渲染几乎零收益（一次 render 内 helper 本就复用）；真实收益只在"循环内 `<include>`"与"同 JVM 多次渲染"。hutool 5.8.18 的 `LRUCache` 线程安全，**降级 hutool 需自行加锁** |
| 二.5 | 包名重命名是**公开 API 破坏**：插件 `ExcelReportPreviewEngine.kt:10-12` 三行 import 需在升级依赖版本时同步（当前依赖 Central 的 1.5.1，不影响现状）。测试包 `exapmle`（应 `example`）仍残留 |
| 三.1 | 每层保存合并结果，pop 直接回滚 O(1) |
| 三.2 | **原建议被否决**：Excel 不认 `sheetFormatPr@defaultRowHeight`（实测显示 20 而非 24），行高必须逐行写 `ht`。原代码被 `!autoHeightRow.isEmpty()` 包住 ⇒ 无 cell height 的模板下 `<defaultRowHeight>` 完全失效，已修 |
| 三.3 | **原假设被否决**：唯一调用点 `CellStyles.toFontStyle` 的 key 集合固定，null 占位不影响相等关系 ⇒ 无命中率收益 |
| 三.6 | **已取消（框架专注复杂报表，大批量报表寻求其他方案）**。实测（POI 5.2.5，单文件探针）：① `SXSSFWorkbook/SXSSFSheet/SXSSFDrawing` 与 `XSSF*` **无继承关系**（`instanceof` 编译不过），`SXSSFDrawing` 没有 `createChart`；② 行序必须单调 —— 写已刷盘行抛 `IllegalArgumentException: Attempting to write a row[0] in the range [0,29] that is already written to disk.`，`getRow()` = null、`SheetUtil.getColumnWidth` = -1（窗口内 22.93 / 未刷盘 21.93 = XSSF 值）；③ 收尾随机行访问实测 NPE（`applyCellWidthHeight` 设行高、图片 `ScaleType` 读 `cellSpanDimension()`，后者被 finalizer try/catch 吞掉 ⇒ 静默失效）；④ 图表：`XDDFDataSourcesFactory.fromXxxCellRange` 只吃 `XSSFSheet`（传 SXSSFSheet 编译失败），改传底层 `XSSFSheet` 也无效——SXSSF 的行**从不落入**底层 XSSFSheet（`getLastRowNum() = -1`，window=10000 同样）⇒ 输出 `<c:f>` 在、`<c:numCache/>` **空**（c:v=0），`fromArray` 手工喂值才出缓存（c:v=6）；⑤ 仍可用的：事后 `setColumnWidth`（`<cols>` 位置正确）、跨刷盘行 `addMergedRegion`、图片 anchor、RichText + XSSFFont；⑥ 必须 `dispose()`（临时文件 `<tmp>/poifiles/poi-sxssf-*`，write 后残留）；⑦ `SXSSFSheet` 无 `setCommitted` ⇒ `SheetStyles.committed` 静默失效 |
| 四.1 | **已取消（扩展面由 XSD 封闭定义）**。`ParserFactory` 13 个 tag 与 XSD `ContainerGroupContainer`（`excel-report-1.0.0.xsd:794-809`）的 `xs:choice` 白名单**逐一对应**（含小写 `include`）；该 choice **无 `xs:any`**、`Style`（`:327-583`）为封闭 `xs:all` ⇒ 新增 Parser = 新增标签 = 违反 XSD。**注**：框架运行期不读 XSD（模板里的 `xsi:schemaLocation` 只被校验器/插件用），所以"框架能不能跑"与"合不合规范"是两件事 —— 目录按 XSD 判定即不合规范 |
| 四.6 | **已取消（同上，且更彻底）**。style key 来源实测：`ReportTemplate:80-82` 把 `<style>` 的**子元素名**当 key（`XmlUtil.getElementNameValueMap`），富文本走 `RichText:62-64` 的属性名 ⇒ key 集 = XSD `Style` 类型的子元素集，自定义 key 必须往 `<style>` 加子元素 ⇒ 违反 XSD；且未注册的 key 会被 `CellStyles.createStyle` **静默丢弃**（`:297` 空 catch），定位成本高 |

## 四、易踩点

- **auto 宽高计算依赖三要素**：cell 的当前内容 + 当前样式 + **是否已 merge**，且靠 `max` 累积 ⇒ **调用顺序就是语义的一部分**。
  实测同一 cell：空白未 merge = -1、有值未 merge = 10.78、有值已 merge = 5.39（POI 对合并块取"整块文本 ÷ 列数"）。
  另：同一 span 多次 `setValue` 时 max 会保留旧的长文本值 ⇒ 列宽偏大（现状即存在）。
- **改 `template.*` 包名/公开类名前**，先 grep `../excel-report-plugin/src`（框架 `AGENTS.md` 硬要求）；插件仓库约定"不要为其编译构建"。
  （已核：插件只用 `template.*` 渲染 + 自带预览渲染器，不碰 `excel.*` / POI 类型 ⇒ 三.6 若动 `excel.*` API 对插件无影响。）
- **SXSSF 流式导出已取消**（三.6）：框架专注复杂报表，大批量报表请用其他方案（POI SXSSF / EasyExcel / 流式 CSV）。
  若有人重新评估，先读"三、备查 三.6"的三条硬约束（类型不兼容 / 行序必须单调 / 刷盘行 `getRow()`=null、`getColumnWidth`=-1）。
- **扩展面是 XSD，不是注册表**（四.1/四.6 已取消）：新增标签、新增样式 key 都等于改
  `schema/excel-report-1.0.0.xsd`（`ContainerGroupContainer` 是封闭 `xs:choice`、`Style` 是封闭 `xs:all`，无 `xs:any`），
  并要同步插件校验/补全。**框架运行期不校验 XSD**（模板里的 `xsi:schemaLocation` 只被编辑器/插件用）⇒ 会出现"能跑但不符合规范"。
- **微基准方法**：交替多轮取最小值 + 充分预热 + `-Xmx2g`，否则 GC/JIT 会让同质两组差 2 倍（本次首版探针即踩到）。

## 五、性能验证建议

1. 构造 3–5 万行 × 10 列数据，分"布局 / 写单元格 / 收尾"三段计时；
2. JFR 或 async-profiler 采样，先确认 `SheetUtil.getColumnWidth` 与合并区扫描的占比（本次实测：这是唯一有数量级差异的热点）；
3. 每项优化单独压测，避免多因子混淆导致无法归因。
