## 复审（同一改动，用户三版迭代，2026-09-29 13:40）

用户在此后自行改了两轮，最终版与前三版的差异（探针均在 `target/probe/`，`mvn clean` 即清）：

| 版本 | `isSupportApplyTarget` 实现 | 实测结果 |
|---|---|---|
| v1 原始 | `Object` 重载 = `keyTarget.isInstance(target)`；`Class` 重载 = `keyTarget.isAssignableFrom(传入类)` | 字体类别被滤空（`filterStyle(map, Font.class) = []`，`getFont = null`）⇒ **8 个 font key 全失效** |
| v2 翻转 | `传入类.isAssignableFrom(keyTarget)`，`Object` 重载委托 `getClass()` | 字体修好，但 **13 个 target=`CellStyle.class` 的 cell key 全失效**（`borderTop` 实测 NONE）——`XSSFCellStyle.isAssignableFrom(CellStyle) = false` |
| v3 **当前** | 对称：`传入类.isAssignableFrom(keyTarget) \|\| keyTarget.isAssignableFrom(传入类)` | **实例判定与类别判定都正确**，字体 + 边框 + 对齐等全部恢复 |

- 关键认知：**实例判定与类别判定方向相反，不能互相委托**。实例：`keyTarget.isInstance(target)`（"实例 ⊆ key 目标类型"）；类别：`category.isAssignableFrom(keyTarget)`（"key 目标类型 ⊆ 类别"）。对称谓词是两者的并集，对实例判定等价于 `isInstance`（且 `StyleApplier.applyStyle` 内部还有一层严格 `isInstance` 兜底），但对**类别**判定过宽。
- **v3 残留（低危，实测）**：`SizeStyleKey` 的 targetType 是 `Object.class`，在对称谓词下 `filterStyle` 的**任何**类别结果都会带上 `preferredSize`；仅含 preferredSize 的 map 现在 `getFont` 返回非 null（旧实现为 null）⇒ `fontPool` 会因 preferredSize 差异多生成一份 Font（输出 styles.xml 多一个 `<font>`，语义无害）。
- 全量 key 回归（`target/probe/Probe4.java`，27 cell + 8 font + 26 sheet）：全部落地；11 个断言 FAIL 经逐条核实**全是探针比对方式问题**（颜色大小写、`XSSFFont.getFontHeight()` 返回 twips 即 20pt→400、`getUnderline()` 返回 short、`margin` 与 `marginLeft` 同写时按 HashMap 顺序后者覆盖前者——旧实现同序，非本次引入）。
