## 弹性布局分配修正（规划阶段）

新建 `doc/flex-layout-allocation.md`（任务规划，4 个任务，未开始执行），对应 `doc/code-review.md` 002。

关键结论（实测，来自 `target/probe/out.txt`）：

- **框架分配弹性高度时手里已有"内容高度"，只是没用**：`VLayout.getSize()` = `sumContainerSize`，
  对固定高度子节点累加声明高度 ⇒ 内容由固定高度子元素组成的包裹层，`getSize().height` 就是内容高度（实测 32/48/32）；
  而 `WeightSizeHelper` 只用 `getSize()` 判断"是否弹性"，分配公式里只有 `weight` ⇒ 112 三等分成 37/37/38。
- 根节点 `onMeasure()` 无参 = `onMeasure(getSize())`，所以根级可用高度**恒等于内容之和**（本例 159）⇒ 顶层不存在"空间不够"，
  纯属分错。
- 方案：`flex-basis = 内容高度`（CSS `flex-basis:content` 语义），剩余按 `weight` 分；放不下时按内容比例压缩并 WARN。
  **内容打平时新旧结果完全等价**（`b + (avail−n·b)/n = avail/n`），行为变化只落在旧算法必然分错的输入上。
- 用户四项决策：改默认语义 / 溢出按内容比例压缩 / 逐节点 WARN 带 tag 链 / HLayout 宽度一起改成同一算法。
- 实现注意：`GridLayout#onLayout` 会二次 `onMeasure`（`:46`），告警要在布局实例内按子容器去重；
  `GridLayout#getContainerGroup` 每次 new 布局且无 `templateNode`，合成布局不能告警（会重复且打错点）。
- 已知局限：`sumContainerSize` 对弹性子节点只记 1 ⇒ 深嵌套时 `basis` 只是下界；与 003（宽度塌陷）同源，后续合并评估。

实测（JDK8 + 真实 POI 链，`target/probe`）：2/3/2 → 32/48/32、无重叠、242 合并区；2/2/2 → 32/32/32 不变、0 告警；
可用高度 100 行（真放不下）→ 3 条 WARN；零尺寸/`PageRowSplit` 模板 → 0 告警。测试 59/60（`SimpleTemplateTest#testLayoutReport`
找 `TestLayoutReport.xlsx.xml` 而资源只有 `TestLayoutReport.xml`，**既有**问题）。

新增易踩点（本轮核实）：

- **`size` 声明的高度对 layout 类子节点不生效**：`VLayout`/`HLayout`/`GridLayout`/`TableComponent` 的 `getSize()` 覆盖成"内容累加"，
  父级 `WeightSizeHelper.getChildSize` 拿到的是内容值而非声明值 ⇒ "把高度写死写小"只对叶子组件成立（`code-review.md` 001 的备选方案因此更不可靠）。
- **弹性分配告警必须只盯弹性子节点**：`PageRowSplitComponent.getSize()=(0,0)`、`Text size="31,0"` 这类占位节点，
  若按"内容至少 1"比较会天天误报（第一版实现就被审查抓到）。
- **根级的"可用高度"恒等于内容之和**（`onMeasure()` = `onMeasure(getSize())`，而 `sumContainerSize` 对弹性子节点累加内容），
  所以顶层永远刚好放下；溢出只可能来自调用方直接给更小的 `Size`、或 `HLayout` 给子节点的高度。
- **`GridLayout#getContainerGroup()` 每次调用都 new 布局**（`getSize()`/`onMeasure`/`onLayout` 各一次），
  任何"按布局实例算一次"的逻辑都要先判 `templateNode()==null` 跳过合成布局，否则重复且打错点。
