# excel-report 框架优化建议

> 分析对象：io.github.mengfly:excel-report:1.5.1
> 分析维度：使用便利性、性能、扩展性

## 一、框架现状

基于 POI + SpEL 的 Excel 报表生成框架，核心设计：

- **模板驱动**：XML 模板 → ContainerTreeNode 树 → ParserFactory 按标签分发 → Container 组件树
- **三段式渲染**：onMeasure（测量）→ onLayout（定位）→ export（写单元格）
- **样式系统**：StyleKey 反射映射到 POI setter，StyleChain 用栈实现层级继承，ReportContext 内做 CellStyle/Font 池化
- **数据注入**：SpEL 表达式 ${...}，DataContext extends HashMap，支持 for/if 流程控制

整体架构清晰、分层合理。问题主要集中在易用性细节、渲染性能热点、以及若干扩展性硬编码上。

## 二、易用性

### 1. TemplateManager 单例非线程安全，且模板每次重新解析
`template/TemplateManager.java:16-22` 双重检查缺失单例，并发下可能创建多个实例。
`getTemplate(id)` 每次调用都重新读流 + DOM 解析，`include` 标签还会级联触发。
**建议**：单例改为 static final 或 holder 模式；对解析结果做缓存。

### 2. 错误处理大量"静默降级"，排查困难
`ContainerParser.getSize`、`ContainerTreeNode.parseJsonStyle`、`CellStyles.createStyle`
（`CellStyles.java:296-299` 直接 catch (Exception ignore) {}）均为 catch 后忽略。
**建议**：引入"严格模式"开关，开发期抛异常并给出行号/标签/属性定位；或提供 template.validate() 汇总 issue 列表。

### 3. 表达式缓存是实例级、无上限控制
`ExpressionHelper.java:20` 的 LRUCache<>(256) 每个实例一份，而 DataContext.Builder.build()
默认 new ExpressionHelper()，导致每次 build 都是新缓存，热点表达式反复走 SpEL 解析。
**建议**：Expression 对象跨实例复用。

### 4. 缺少 Builder / Fluent API 的入口
ExcelReport 目前是 new + exportTemplate + save 的命令式用法。
**建议**：补充链式入口，降低入门成本。

### 5. 拼写与可读性瑕疵
包名 exepression（应为 expression）、字段 syleMap（ContainerTreeNode.java:35）、
getContainerGrop（GridLayout.java:79）等拼写错误，影响自动补全体验。

## 三、性能

### 1. ~~StyleChain.onStyle 每次调用都全量重建 StyleMap（最大热点）~~ ✅ 已解决
`style/StyleChain.java:35-39` 的 curStyle() 遍历整个栈重新合并 HashMap。
onStyle 在每个组件 export 时都会调用一次（Container.java:57）。
**原建议**：用 ArrayDeque + 缓存 currentStyle，push 时增量 merge、pop 时回滚；
或改用不可变层的 CombinedStyleMap，查询时按需查找。

**实现**：已改为单栈 `Deque<StyleMap> mergedStack`，每层保存"该层合并后的完整样式表"。
- push：`mergedStack.push(mergeInto(mergedStack.peek(), style))`，只合并当前层，O(key 数)；
- pop：`while (size > depth) pop()`，直接弹回父层结果，O(1)，零重建；
- 原 `styleChain` 栈退化为纯计数器后已删除（`mergedStack` 长度与其完全同步）；
- `getStyle()` 返回 `mergedStack.peek()`，栈空时返回空 StyleMap。

每次 onStyle 由 O(栈深 × key 数) 降为 O(key 数)。

### 2. ReportContext.applyCellWidthHeight 在自动行高时遍历全表
`ReportContext.java:128-140`，当设置 defaultRowHeight 且存在 autoHeight 行时，
遍历 firstRowNum..lastRowNum 逐行 setHeightInPoints，大表下是 O(rows) 额外开销。
**建议**：只记录需要设置的行区间，或与写入过程合并。

### 3. CellStyle 池化 key 用 StyleMap，但 getStyleMap 会把缺失 key 塞 null
`StyleMap.java:28-34` 缺失时放入 null，导致等价样式因 null 占位不同产生不同 key，
池命中率被拉低。
**建议**：getStyleMap 跳过 null 值，提升池命中率。

### 4. RichText/SheetUtil.getColumnWidth 的 auto 宽度计算成本高
`ExcelCellSpan.java:107-109` 在 width=auto 时对每个单元格调用 SheetUtil.getColumnWidth，
内部做字体渲染宽度估算，非常耗 CPU，每写一个 cell 都触发。
**建议**：支持按列批量计算，或加开关/缓存。

### 5. ExcelCellSpan 构造与 setStyle 双重遍历单元格区域
构造函数先 createOrGetCell 建一遍（ExcelCellSpan.java:41-46），setStyle 又遍历一遍。
merge() 每单元格调 sheet.addMergedRegion，POI 合并区域列表是线性的，大量合并会退化。

### 6. POI 大文件写出
ExcelReport 用 XSSFWorkbook（ExcelReport.java:32），全内存 DOM，几十万行易 OOM。
**建议**：提供 SXSSFWorkbook 流式导出策略选项。

## 四、扩展性

### 1. ParserFactory 静态注册，无法运行时扩展/覆盖
`ParserFactory.java:12-35` 用 static Map + static block 硬编码 13 个 Parser，addParser 同名抛异常。
**建议**：改为实例级注册表，或提供 SPI/ServiceLoader 机制；支持覆盖注册；引入 ParserRegistry 接口。

### 2. 组件只支持 POI 绑定，输出格式被锁死
StyleKey 通过方法名字符串反射调用 setter（CellStyles.java:43），
无法静态校验、强耦合 POI setter 命名、无法支持 CSV/HTML/PDF。
**建议**：把 apply 逻辑改为函数式（BiConsumer），名字字符串仅作为 XML key。

### 3. ReportTemplate 与 TemplateManager 双向绑定，模板不可复用
TemplateManager.getTemplate 给模板注入 this（TemplateManager.java:38），
render 又依赖它做 include，导致模板对象与 manager 生命周期耦合，难以缓存共享。
**建议**：把 TemplateManager 作为 render 的显式参数传入。

### 4. 缺少 Sheet 级并行的导出能力
导出是单线程串行，但每个 ReportContext 绑定一个 sheet，多 sheet 天然可并行。
**建议**：提供 exportAsync 或批量 exportSheets 接口。

### 5. Container 接口职责偏多
Container extends StyleAble，同时承担 templateNode、尺寸/位置、onMeasure/onLayout/onExport 五类职责。
**建议**：拆成 Measurable / Layoutable / Exportable / StyleAble 的 mixin。

### 6. SheetStyles / CellStyles 注册表不可扩展
两个 map 都是 private，只有私有 register 方法，用户无法注册自定义 StyleKey。
**建议**：暴露 registerStyleKey(StyleKey) 公共方法。

### 7. Image 体系与网络图片缺少超时/校验
ReportContext.addPicture（ReportContext.java:113-117）直接 IoUtil.readBytes，
UrlImage 走网络无超时设置。
**建议**：加超时参数与失败降级。

## 六、附录：性能评估建议

在大表场景下，建议按以下顺序验证优化效果：
1. 构造 3-5 万行 × 10 列的测试数据，分列导出/布局/写单元格三段计时；
2. 用 JFR 或 async-profiler 采样，确认 StyleChain.curStyle 与 SheetUtil.getColumnWidth 的耗时占比；
3. 每项优化单独压测对比，避免多因子混在一起导致效果无法归因。
