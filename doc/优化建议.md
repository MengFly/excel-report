## 二、待办

### P1 · 三.4 auto 列宽计算（真热点）

**现状**：结果累积是增量的（`cellAutoWidth.compute(max)`），**计算不是** —— 每次都调 `SheetUtil.getColumnWidth` 全量重算，
且 `setStyle` 与 `setValue` 各触发一次。成本（1000 行×3 列，Arial 12pt）：

| 合并区数 | 逐 cell 调用 | 按列一次调用 |
|---|---|---|
| 0 | 24.35 µs/cell | 15.05 µs/cell（-38%） |
| 1000 | **541 µs/cell** | 39.86 µs/cell（-93%） |

单次调用固定开销 ≈ 9.3 µs（无合并）；1000 合并区时 ≈ 517 µs/次（**每次都要 `sheet.getMergedRegions()` 复制整个合并区列表**）。
外推 1000 行×10 列全 auto：无合并 487 ms → 150 ms；1000 合并区 10.8 s → 0.4 s。

**⚠️ 正确性前提（否则会改坏结果）**：现状语义是"**只对带 `width=auto` 样式的 cell** 度量再取 max"，
而 POI 的 `getColumnWidth(sheet, col, true, firstRow, lastRow)` 会算区间内**所有** cell。
实测反例：20 行列宽 —— 只算第 0 行 = **2.71**，整列算 = **28.54**（撑大 10 倍）；全行都带 auto 时两者一致。

**已做（方案 1：延迟到终态算一次）** ✅ `f577599`，约 20 行、无 API 变更：

| 文件 | 改动 |
|---|---|
| `ExcelCellSpan` | 新增 `autoSizeCalculated`；`setStyle` 不再计算（只记 `styleMap`）；新增 `calculateAutoSizeIfAbsent()` |
| `ReportContext` | 新增 `cellSpans` 列表并在 `getCellSpan` 登记；`applyCellWidthHeight` **开头**补算未算过的 span |

为什么不能简单删掉 `setStyle` 那次：`SpanComponent` / `ChartComponent` 只 `merge()` 不 `setValue`。
实测 `setStyle` 那次返回 **-1**（cell 空白未 merge，`+4` 后 = 3 的垃圾值），必然被 `setValue` 的终态值覆盖。
**等价性三重验证**：① 真实模板导出改动前后 `sheet1.xml`（含 `<cols>`）**逐字节相同**；
② 只 merge 场景 768 = 768；③ 有值场景 2798 = 2798。收益 **-50%**（48.7 → 24.35 µs/cell）。

**待做**：
- 方案 2 **条件批量**（再降到 ~15 µs/cell）：统计每列"auto cell 数 == 非空 cell 数"才整列一次算，否则退回逐 cell；
- 方案 3 **自实现度量**（收益最大）：POI 的 `getCellWidth` 是 private，想做到"只算 auto cell 的批量"只能自己复制
  `AttributedString`/`TextLayout` + 合并区逻辑，并复用 `FontRenderContext`、自维护合并列表；需与 POI 结果做等价性回归。

### ~~P1 · 四.1 注册表可扩展（SPI）~~ ❌ 已取消（2026-09-29）

**取消理由**：`ParserFactory` 的 13 个 tag（`Text`/`Table`/`Image`/`List`/`HLayout`/`VLayout`/`Link`/`Chart`/`Span`/`include`/`PageRowSplit`/`PageColSplit`/`GridLayout`）
与 XSD `ContainerGroupContainer`（`excel-report-1.0.0.xsd:794-809`）的 `xs:choice` 白名单**逐一对应**；
该 choice **没有 `xs:any`**，`Style`（`:327-583`）也是封闭的 `xs:all`。⇒ 新增 Parser = 新增 XML 标签 = 违反 XSD，
"注册表开放"解决不了 schema 层面的问题。真有自定义需求，只能 fork/扩展 XSD 并同步插件校验（属框架协议变更，不是 SPI 改造）。

### P2 · 二.2 严格模式 / 模板校验 ✅ 本次

**原描述被实测修正**：静默路径不是"只剩 2 处 catch"，共 **9 条**（探针逐条跑真实模板）。其中只有 2 条是 catch，
其余是 `if (x != null)` 式的静默跳过：

| # | 场景 | 实测表现 | 位置 |
|---|---|---|---|
| 1 | 组件上未知属性 | 静默忽略 | `BeanUtil.initBeanProperties` |
| 2 | 属性值转换/写入失败 | catch 吞掉 | `BeanUtil.java:59` |
| 3 | `<style>` 未知 key | 静默丢弃 | `CellStyles.createStyle` |
| 4 | `<style>` 值无法转换（`fontHeight=abc`、**`${h}`**） | catch 吞掉 | `CellStyles.java:189` |
| 5 | 布尔值写错（`fontBold=notabool`） | **强制转成 `false`** | `StyleKey.getStyle` |
| 6 | `style` 引用不存在的 id | 返回空样式 | `ContainerTreeNode.getStyleById` |
| 7 | `<container>` 下多个兄弟组件 | 只渲染第一个 | `ReportTemplate.buildTemplateNodeTree` |
| 8 | `<sheetStyle>` 未知 key | 静默忽略 | `ReportTemplate.initSheetStyle` |
| 9 | 未知标签 | 抛异常，但无模板名/行号 | `ParserFactory.getParser` |

**实现**（`template/validate/TemplateValidator`，两层互补、都不复制白名单）：

- **L1 结构层**：按 XSD 校验标签 / 属性 / 样式 key / 枚举。**直接用原始字节做校验**——
  实测传 DOM 时 `SAXParseException.getLineNumber()` 恒为 **-1**（DOM 不带行号），传字节才有真实行号。
  `Schema` 静态缓存（`Validator` 非线程安全，每次新建）；XSD 加载失败只降级为一条 WARN，**不让框架自身的 schema 问题拖垮模板**。
- **L2 语义层**：XSD 结构上表达不了的——样式 id 交叉引用、`<container>` 基数、内联 JSON 的 key 与语法、
  样式取值转换、`for` 缺 `变量:` 绑定、颜色回退黑色。只向既有注册表（`CellStyles`/`SheetStyles`）查存在性；
  颜色的复判也用 `ColorStyleKey` 同款来源（`HSSFColorPredefined` + `HexUtil`），**没有另建名单**（这正是"线上 XSD 漏 `GridLayout`"那类漂移病的解药）。

**模式**（按需选择，默认宽松）：

- 默认**宽松**：解析照常、渲染照常（存量行为不变），首次 `render` 打**一条**汇总 WARN（实测只打 1 次）；
- 严格：`TemplateManager#setStrict(true)` ⇒ `getTemplate` 抛 `TemplateValidationException`（带 issue 清单）。
  判定放在缓存之外，所以**运行期打开严格模式对已缓存的模板同样生效**（否则行为取决于调用顺序）。

**无命名空间的模板不能一棒打死**：实测无 `xmlns` 的模板当前**完全能跑**，而 XSD 的 `elementFormDefault="qualified"`
会直接拒掉它 ⇒ 这种情况只出 WARN（"已跳过结构校验"）、L2 照跑，不判 ERROR。

**L2 覆盖不到、留给离线脚本的**：`StyleUtil` 那类"启发式坑"（`Span`/`Chart` 上的 `width:auto`、
`Table`/`List` 写正数 `size`、内联 `${}` 未加引号、样式定义后未引用）——它们是"可能不是本意"而非"一定失效"，
留在 `check_template.py` 里更合适。

**验证**：`mvn -o clean test` **30/30 通过**（新增 17 条规则用例 + 4 条严格模式用例 + 4 条 XSD 用例）。
自带 7 个模板与技能的两个正例 `standard-table.xml`/`grouped-report.xml` 均 **0 ERROR / 0 WARN**（无误报）；
技能负向夹具 `self-test-broken.xml` 报 **25 ERROR**（18 条 XSD + 7 条语义，两条规则集各抓到对方抓不到的）。
反向验证：临时停用 `style.undefined-id` 规则 ⇒ 恰好 2 个对应用例失败（证明用例非空转）。

**顺带修掉一个"测试不可重复"的既有缺陷**（`TestTemplate.after`）：该用例保存 `example/test-template.xlsx` 后
用 `DesktopUtil.open` 调系统默认程序打开它，窗口会一直持有文件句柄 ⇒ **第二次 `mvn test` 必然失败**
（实测报 `另一个程序正在使用此文件`），CI / 无桌面环境同样失败。已去掉那次自动打开（`report.save` 保留，
需要肉眼检查时手动打开即可）。

**API 影响：纯新增，无破坏**。新增 `TemplateValidator`/`ValidationIssue`/`TemplateValidationException`；
`ReportTemplate` 加 `validate()`/`hasErrors()`；`TemplateManager` 加 `setStrict`（Lombok 生成）。
插件只用 `template.*` 渲染、不加载 XSD ⇒ **插件零影响**。

**顺带修掉一处"注定的失败转换"**（`ListParser.getIgnoreProperties` 补 `style`）：
`ListHeader` 继承 `StyleHolder`，其 `style` 是 **final 只读** 属性（`StyleMap`），而 `<header style="{fontBold:true}">`
是合法的（XSD 允许、样式也确实生效）——样式由 `ListParser` 里显式的 `header.addStyle(headerNode.getStyle(...))` 应用。
但 `ListParser` 初始化 header bean 时没像其它 Parser 那样忽略 `style`，于是每次渲染都要走一遍
"String → final StyleMap 字段"的必然失败转换，再被 catch 吞掉。
**这是把 catch 改成 WARN 之后实测暴露的**：`TestTemplate.xml` 的两个 `<header style=...>`（`:73`、`:81`）
每渲染一次就打 2 条假告警（实测一次全量测试共 4 条），不修就等于用噪声换安静 ⇒ 已修
（实测改后全量测试告警数 **0**，且 `<header>` 样式仍生效：`{fontBold=true, alignHorizontal=CENTER}`）。
**教训**：去掉静默要连带把"本来就注定失败、且失败无害"的路径清掉，否则信号会被噪声淹没。

### ~~P2 · 三.6 SXSSF 流式导出~~ ❌ 已取消（2026-09-29）

**取消理由**：框架定位是**复杂报表**（合并区 / 多列布局 / 图表 / 图片 anchor / 精确宽高），
与 SXSSF 的"行序单调 + 行刷盘后可随机访问失效"根本冲突：只换 workbook 无法完成流式，
彻底方案要动 `Container` 的写单元格方式（改走"行模型 / CellSink"中间层），代价与收益不成比例。
**大批量报表请走其他方案**：直接用 POI SXSSF / EasyExcel（FastExcel）/ 流式 CSV，或先落库再导出。
实测依据归档在"三、备查"（仅当以后重新评估时再读）。

## 三、已完成项的关键结论（备查）

| 编号 | 结论 |
|---|---|
| 二.1 | 单例 + `ConcurrentHashMap` 缓存；`ReportTemplate` 已无共享可变字段，但**同模板多线程 render 尚无用例验证** |
| 二.3 | 静态共享缓存替代实例缓存。单次渲染几乎零收益（一次 render 内 helper 本就复用）；真实收益只在"循环内 `<include>`"与"同 JVM 多次渲染"。hutool 5.8.18 的 `LRUCache` 线程安全，**降级 hutool 需自行加锁** |
| 二.5 | 包名重命名是**公开 API 破坏**：插件 `ExcelReportPreviewEngine.kt:10-12` 三行 import 需在升级依赖版本时同步（当前依赖 Central 的 1.5.1，不影响现状）。测试包 `exapmle`（应 `example`）仍残留 |
| 三.1 | 每层保存合并结果，pop 直接回滚 O(1) |
| 三.2 | **原建议被否决**：Excel 不认 `sheetFormatPr@defaultRowHeight`（实测显示 20 而非 24），行高必须逐行写 `ht`。原代码被 `!autoHeightRow.isEmpty()` 包住 ⇒ 无 cell height 的模板下 `<defaultRowHeight>` 完全失效，已修 |
| 三.3 | **原假设被否决**：唯一调用点 `CellStyles.toFontStyle`（四.2 后改名 `filterStyle`）的 key 集合固定，null 占位不影响相等关系 ⇒ 无命中率收益 |
| 三.6 | **已取消（框架专注复杂报表，大批量报表寻求其他方案）**。实测（POI 5.2.5，单文件探针）：① `SXSSFWorkbook/SXSSFSheet/SXSSFDrawing` 与 `XSSF*` **无继承关系**（`instanceof` 编译不过），`SXSSFDrawing` 没有 `createChart`；② 行序必须单调 —— 写已刷盘行抛 `IllegalArgumentException: Attempting to write a row[0] in the range [0,29] that is already written to disk.`，`getRow()` = null、`SheetUtil.getColumnWidth` = -1（窗口内 22.93 / 未刷盘 21.93 = XSSF 值）；③ 收尾随机行访问实测 NPE（`applyCellWidthHeight` 设行高、图片 `ScaleType` 读 `cellSpanDimension()`，后者被 finalizer try/catch 吞掉 ⇒ 静默失效）；④ 图表：`XDDFDataSourcesFactory.fromXxxCellRange` 只吃 `XSSFSheet`（传 SXSSFSheet 编译失败），改传底层 `XSSFSheet` 也无效——SXSSF 的行**从不落入**底层 XSSFSheet（`getLastRowNum() = -1`，window=10000 同样）⇒ 输出 `<c:f>` 在、`<c:numCache/>` **空**（c:v=0），`fromArray` 手工喂值才出缓存（c:v=6）；⑤ 仍可用的：事后 `setColumnWidth`（`<cols>` 位置正确）、跨刷盘行 `addMergedRegion`、图片 anchor、RichText + XSSFFont；⑥ 必须 `dispose()`（临时文件 `<tmp>/poifiles/poi-sxssf-*`，write 后残留）；⑦ `SXSSFSheet` 无 `setCommitted` ⇒ `SheetStyles.committed` 静默失效 |

## 四、易踩点

- **auto 宽高计算依赖三要素**：cell 的当前内容 + 当前样式 + **是否已 merge**，且靠 `max` 累积 ⇒ **调用顺序就是语义的一部分**。
  实测同一 cell：空白未 merge = -1、有值未 merge = 10.78、有值已 merge = 5.39（POI 对合并块取"整块文本 ÷ 列数"）。
  另：同一 span 多次 `setValue` 时 max 会保留旧的长文本值 ⇒ 列宽偏大（现状即存在）。
- **改 `template.*` 包名/公开类名前**，先 grep `../excel-report-plugin/src`（框架 `AGENTS.md` 硬要求）；插件仓库约定"不要为其编译构建"。
  （已核：插件只用 `template.*` 渲染 + 自带预览渲染器，不碰 `excel.*` / POI 类型 ⇒ 三.6 若动 `excel.*` API 对插件无影响。）
- **SXSSF 流式导出已取消**（三.6）：框架专注复杂报表，大批量报表请用其他方案（POI SXSSF / EasyExcel / 流式 CSV）。
  若有人重新评估，先读"三、备查 三.6"的三条硬约束（类型不兼容 / 行序必须单调 / 刷盘行 `getRow()`=null、`getColumnWidth`=-1）。
- **扩展面是 XSD，不是注册表**（四.1/四.6 已取消）：新增标签、新增样式 key 都等于改
  `schema/excel-report-1.0.0.xsd`（`ContainerGroupContainer` 是封闭 `xs:choice`、`Style` 是封闭 `xs:all`，无 `xs:any`），
  并要同步插件校验/补全。**框架自 二.2 起会在解析期按 XSD 校验**（`TemplateValidator`，默认只汇总 issue、不中断），
  但模板里 `xsi:schemaLocation` 指向的仍是**线上那份** XSD ⇒ 改 schema 必须同时发布线上版本，否则编辑器侧与框架侧会不一致。
  实测教训：线上 XSD 曾长期**无法编译**（`Table@headerHeight` 的 `default="true"` 对 `xs:int`、`ChartValueAxis/data` 重复声明 `title`），
  ⇒ 编辑器基于 `schemaLocation` 的校验其实一直是失效的；同一时期线上版还漏了 `GridLayout`，会把合法模板判非法。
  实测已抓到一例：XSD `Style` 原本**没有** `fillBackgroundColor`，而 `CellStyles` 一直注册着该 key（`fillBackgroundColor` 在 XSD 里从来只对应 POI 的 `setFillBackgroundColor`）
  ⇒ 2026-09-29 已补进 XSD（补后 `Style` 32 个子元素与 `CellStyles` 除内部 `preferredSize` 外一一对应）；**插件 `StyleKeyInfo.kt` 的镜像清单仍缺该 id，待插件侧同步**。
- **样式 key 的"实例判定"与"类别判定"方向相反，不能互相委托**（四.2 实测，同一处返工 3 轮）：
  实例判定 = `keyTarget.isInstance(target)`（"实例 ⊆ key 目标类型"）；类别判定 = `category.isAssignableFrom(keyTarget)`
  （"key 目标类型 ⊆ 类别"，`CellStyles.filterStyle` 用）。**写反任一处都静默失效**，两例实测：
  ① `filterStyle(map, Font.class)` 传的是父接口 `Font` 却按"传入类 ⊑ key 目标类型"判定 ⇒ 8 个 font key 全丢，
  `ReportContext.getFont` 返回 **null**、`cellStyle.getFontIndex()` = 0（字体样式整体失效）；
  ② `Object` 重载委托给类别判定 ⇒ 13 个 target=`CellStyle.class` 的 cell key 全丢（`XSSFCellStyle.isAssignableFrom(CellStyle)` = **false**），
  边框/对齐/自动换行/旋转/缩进/填充全部不生效。
  现实现用对称谓词 `a.isAssignableFrom(b) || b.isAssignableFrom(a)` 同时覆盖两种用途 —— 对**实例**判定等价于 `isInstance`
  （且 `StyleApplier.applyStyle` 内部还有一层严格 `isInstance` 兜底），但**类别判定会过宽**：key 的目标类型与查询类别互为父子都会被收进来。
  实测影响面：`SizeStyleKey` 的 targetType 现为 `CellStyle.class` ⇒ `filterStyle(map, CellStyle.class)` 会带上 `preferredSize`
  （其 apply 是空 lambda，无副作用）；当前唯一在用的 `filterStyle(map, Font.class)` **不受影响** —— `Font` 与 `CellStyle` 无父子关系，
  只返回字体 key。⇒ 若将来新增 `filterStyle(..., CellStyle.class)` 的调用点，需先决定 `preferredSize` 该不该出现在结果里。
- 四.2 后 `StyleKey.applyStyle` 类型不匹配时**不再打 `log.error`**（旧实现会记一条），完全静默 ⇒ 新增/改 key 时 targetType 写错
  只能从样式落地结果反推。判定路径现已收敛为**一条**：`CellStyles.initStyle` 与 `SheetStyles.initStyle` 都走
  `StyleRegistry.initStyle`（先按"实例是否属于 key 目标类型"过滤，再 apply），不再有"某条路径不预过滤"的分叉。
- **`CellStyles` / `SheetStyles` 刻意不并表**（四.2 后评估过一轮）：两者 key 集分别镜像 XSD `Style`(32) / `SheetStyle`(27)，
  子元素交集为空（实测 Java 侧同为 33 / 27、交集空）。共用逻辑可以抽（已抽到 package-private 的 `style/StyleRegistry.java`），
  但**必须各持一份实例**：并表会让"key 写错上下文"从"查不到 ⇒ 丢弃"变成"进 `StyleMap` ⇒ 事后被类型过滤静默丢弃"，
  改变 `StyleMap.equals` ⇒ 影响 `cellStylePool`/`fontPool` 这类以样式表为 key 的池命中。
  两份 `DEFAULT_STYLE`（cell 默认 20 项 / sheet 默认 `defaultRowHeight=20f`）也不能合并 —— 由 `ExcelReport:60`/`:63` 分别消费，方向不能互串。
- **微基准方法**：交替多轮取最小值 + 充分预热 + `-Xmx2g`，否则 GC/JIT 会让同质两组差 2 倍（本次首版探针即踩到）。

## 五、性能验证建议

1. 构造 3–5 万行 × 10 列数据，分"布局 / 写单元格 / 收尾"三段计时；
2. JFR 或 async-profiler 采样，先确认 `SheetUtil.getColumnWidth` 与合并区扫描的占比（本次实测：这是唯一有数量级差异的热点）；
3. 每项优化单独压测，避免多因子混淆导致无法归因。
