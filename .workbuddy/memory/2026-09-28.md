## 表达式缓存的跨模板共享安全性分析

结论：`ExpressionHelper` 的缓存（`LRUCache<String, TemplateExpression>`）**可以安全跨模板共享**，不会出现表达式解析异常。

论证要点（供后续讨论复用）：

1. **缓存的是 AST，不是求值结果**。三个实现类字段全为 final 且不引用 `DataContext`：
   - `NotExpression` → 只持 `String`
   - `StandardExpression` → 只持 SpEL `Expression`（不可变 AST）
   - `ComposeExpression` → 只持 `List<TemplateExpression>`
2. **数据绑定在求值期**：`StandardExpression.evaluate(ctx)` → `expression.getValue(getEvaluationContext(dataContext))`，而 `TemplateExpression.getEvaluationContext`（`:19-24`）是 default 方法，**每次新建** `StandardEvaluationContext`，rootObject 为当次 dataContext。Spring `Expression` 官方语义即"解析一次、多 context 多次求值"。
3. **解析结果只依赖字符串**：`ExpressionHelper:19` 的 `parser` 是 static `SpelExpressionParser`，无按模板/上下文的配置差异。
4. **插件降级逻辑不串味**：`PreviewExpressionHelper` 的"取不到值降级为原文"写在 `doExpression`（求值期）override 里，包在 `super.doExpression` 外层；缓存的 `TemplateExpression` 只是其内部实现细节 → 跨 helper 共享不改变求值语义。

两个必须守的前提（破坏任一则共享不再安全）：

- **A**：`ExpressionHelper.onCreateExpression`（`:33`，protected 空钩子，缓存未命中时回调）不得被用于挂实例级状态 —— 共享后只有"首次解析者"能收到回调。当前框架与插件均未 override。
- **B**：`TemplateExpression.getEvaluationContext` 不得被 override 成复用同一个 `StandardEvaluationContext`（该类非线程安全）。当前未 override。

hutool 版本相关（已用 javap 反编译核实）：

- hutool 5.8.18 的 `LRUCache extends ReentrantCache`，是**线程安全**的：`ReentrantCache.get(K,boolean)` 用 `ReentrantLock` 全锁；`AbstractCache.get(K,boolean,Func0)` 用 `keyLockMap.computeIfAbsent` 做**按 key 加锁**的回填（不同表达式可并发解析）。
- ⚠️ 早期 hutool 的 `LRUCache` 直接继承 `AbstractCache`，无 ReentrantLock，**非线程安全**。若降级 hutool 版本，共享缓存须自行加锁。

唯一当前就成立的问题：`ExpressionHelper:70-72` 把**解析失败**降级为 `NotExpression` 并**缓存**，即"解析失败"被固化（改模板不会重新解析，除换字符串或清缓存）。语义确定，不算跨模板异常。

## 方案取舍：`ExpressionHelper.getInstance()` 单例 vs 静态共享缓存

**推荐静态共享缓存，不做单例。** 关键理由：插件用 `new PreviewExpressionHelper(warnings)`（每 render 一份，因持有 per-render 的 `warnings` 列表），单例只覆盖默认路径 → 插件拿不到共享缓存，优化对插件完全失效。改成**类内 static 缓存**后，插件的子类实例自动复用同一缓存，且 `DataContext` 一行不用改。

```java
private static final Cache<String, TemplateExpression> SHARED = new LRUCache<>(2048);
private final Cache<String, TemplateExpression> expressionMap;
public ExpressionHelper() { this(SHARED); }
protected ExpressionHelper(Cache<String, TemplateExpression> cache) { this.expressionMap = cache; }
```

兼顾：默认共享 / 子类可隔离（走 protected 构造）/ 可测试注入 / 插件零改动。

单例方案的缺陷：
1. 可扩展类 + 单例互斥（有实例状态的子类如 `PreviewExpressionHelper` 无法是单例）；
2. 无法注入 mock，测试不可隔离；
3. 将来若要按场景配 `SpelParserConfiguration`，单例是全局的改不动；
4. IntelliJ 多插件各自带一份框架 jar 时静态字段会有**多份** `instance`，"单例"实际不唯一（对缓存只是没共享，不影响正确性）。

无论哪种方案，`onCreateExpression` 钩子都需处理（共享后只有"首次解析者"收到回调）。当前为空钩子，框架与插件均未 override。

配置细节：`new LRUCache<>(256)` 的 timeout 为 0（永不过期），仅受容量约束；改为全局共享后容量应上调（256 → 1024/2048）。

## 收益定位修正（重要，勿高估）

用户质疑"单模板提升不明显"，结论：**确实如此**。

- 一次 render 内 helper 是复用的（`ForExpression.createForEnv` → `createChildContext` 复用父 helper；`NoneExpression`/`IfExpression` 直接透传 context），所以同一 render 内重复表达式**本来就已经命中缓存**。例：Table 100 行 × 3 列 ≈ 600 次 `doExpression`，不同字符串仅约 6 个 → 实例缓存已给 ~99% 命中率。
- **唯一在"单模板单次渲染"内的真实收益**：`IncludeParser:33` 每次 include 调用都 `new DataContext()` → 新 helper → **新缓存**，导致 `<include>` 位于循环内时，每轮迭代重新解析该 include 模板的全部表达式。量级 = 迭代数 × include 表达式数 × ~10–30 µs。与 TemplatesManager 模板缓存叠加，才是完整的"循环 include 去重"。
- 其余收益在"跨渲染"维度（报表服务 / 批量导出 / 插件反复预览）：(渲染次数 − 1) × 不同表达式数 × ~10–30 µs。
- 模板通常 20–200 个不同表达式 → 单次渲染省 0.2–6 ms。大表（数百 ms）占比 <1%，小报表可能占百分之几十。

**定位**：不是性能优化，是消除重复劳动。20 行 + 零 API 破坏，做了不亏，但不该按 P1 排期。真正有数量级差异的是三.2（auto 列宽 `SheetUtil.getColumnWidth`）与三.6（SXSSF）。

已在 `doc/优化建议.md` 二.3 加入"收益定位（诚实评估，勿高估）"小节，并把五、优先建议下的"已完成"行从 P1 改为中性表述。
